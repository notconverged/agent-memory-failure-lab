# Stage 0 baseline evaluation isolation specification

## 1. Product evaluation question

Stage 0 is the product's first evaluation foundation. It asks one narrow question:

> Under one fixed DSH harness, can an explicitly injected cross-session memory
> payload improve a Coding Agent's behavior between two fresh sessions?

The result is evidence for product decisions, not by itself a claim that a
complete memory product is useful in every coding workflow.

Stage 0 does not study memory extraction, semantic retrieval, plugins,
embeddings, vector databases, RL memory policies, or model comparisons. The
memory is a benchmark oracle fact generated by the host controller. This
isolates memory utilization from memory construction.

The planned DSH baseline is `v0.1.0-rc.7`, commit `99f6f02`, in Windows native
headless mode. The authoritative CLI reference is the [DSH CLI
README](https://github.com/deepseek-ai/deepseek-harness/blob/master/apps/cli/README.md).

## 2. Episode definitions

One episode is one fresh DSH subprocess, one fresh persisted session, one fresh
workspace, and one task. The experiment has three roles:

| Session | Task | Memory | Purpose |
| --- | --- | --- | --- |
| `S1_seed` | `E1` / `calculate_return` | none in the prompt | Seed an independent experience and close the session. |
| `S2_control` | `E2` / `calculate_drawdown` | `No relevant prior experience is available.` | Control condition. |
| `S2_memory` | `E2` / `calculate_drawdown` | Canonical oracle fact `R1` | Treatment condition. |

After `S1_seed` closes, the controller writes exactly this canonical fact:

```json
{
  "id": "R1",
  "content": "Financial calculations must use Decimal, not float.",
  "source_episode": "E1",
  "valid_from": "E1",
  "valid_until": null
}
```

The same `R1` is reused for all confirmation episodes. The full S1 trajectory
is never copied into the memory channel.

## 3. Fixed variables and treatment variable

The following must be identical for `S2_control` and `S2_memory`:

- DSH commit and effective config hash;
- runtime mode, platform, provider, model, protocol, temperature,
  reasoning effort, token limit, and the declared `max_steps` limit;
- system prompt, prompt template, task text, task order, and tool schema;
- benchmark template and workspace snapshot;
- maximum steps and tool timeout;
- fresh-session and fresh-workspace creation procedure.

The only treatment variable is the content of the fixed
`<MEMORY_CONTEXT>...</MEMORY_CONTEXT>` block. The block is present in both
conditions, so a condition cannot be identified merely by a changed prompt
shape.

## 4. Fixed DSH harness

`configs/minimal.cordis.yml` is the sole Stage 0 harness. It keeps the agent
loop, model-facing bash/editor tools, and JSONL session persistence. It turns
off workspace context, runtime identity context, skills, job tools, and bash
tool aliases not required by the task. It contains no memory plugin and no
`memory_search`, `memory_write`, or `memory_forget` tool.

Before a real run, inspect the effective configuration rather than relying
only on the YAML file:

```powershell
dsh --profile headless --patch configs/minimal.cordis.yml --dump-config
```

The run manifest must record:

```json
{
  "dsh_version": "v0.1.0-rc.7",
  "dsh_commit": "99f6f02",
  "runtime_mode": "headless",
  "platform": "windows",
  "node_version": "...",
  "pnpm_version": "...",
  "provider": "...",
  "model": "...",
  "temperature": 0,
  "reasoning_effort": "...",
  "max_tokens": "..."
}
```

The effective evidence also includes config, system-prompt, tool-schema, task,
and workspace snapshot hashes.

The runner fixes `max_steps` to 24 by default and passes it through
`DSH_MAX_STEPS`; if a DSH release does not expose that setting in its effective
config, the run must be treated as requiring manual review rather than assumed
to be equivalent.

## 5. Fresh-session and clean-workspace rules

Every invocation uses a new subprocess, new session id, new session root, and
new DSH home directory. The runner never supplies `resume` or `fork`, never
reads a previous episode's DSH directory, and never copies a previous
workspace into a later episode.

Each workspace starts by copying only `benchmarks/decimal_transfer/template`.
The controller records the initial workspace hash. A result is invalid if the
initial `S2_control` and `S2_memory` workspace hashes differ.

## 6. Host-managed memory injection

The controller renders the same prompt structure in both S2 conditions:

```text
<MEMORY_CONTEXT>
{payload}
</MEMORY_CONTEXT>

<CURRENT_TASK>
{task text}
</CURRENT_TASK>
```

No memory API is exposed to the model. `R1` enters the treatment prompt only
after S1 is complete, and its payload hash is written to `memory_events.jsonl`.
The control payload is a fixed no-memory statement and has a different payload
hash. No other persistent or implicit memory channel is allowed.

Forbidden channels include DSH memory plugins, MCP, skills, goals, session
resume, session fork, previous-session references, shared mutable workspace
files, hidden benchmark files, copied traces, and API keys or secrets in
results.

## 7. Result schema and metrics

Each episode records `run_id`, condition, session id, initial workspace hash,
task id, memory channel metadata, harness hashes, behavior metrics, and host
verifier output. The primary metric is:

```text
first_attempt_compliance
```

It is true only when the first implementation written before verifier feedback
uses the required `Decimal` behavior. Secondary metrics are
`memory_visible`, `memory_utilized_before_feedback`, `tests_to_success`,
`steps_to_success`, and `final_success`.

The confirmation comparison is:

```text
delta = P(first_attempt_compliance | relevant_memory)
      - P(first_attempt_compliance | no_memory)
```

## 8. Runs

Dry-run preparation:

```powershell
python scripts/run_episode.py --dry-run --condition no_memory
python scripts/run_episode.py --dry-run --condition relevant_memory
```

One smoke run executes one `S1_seed`, one control episode, and one treatment
episode:

```powershell
python scripts/run_episode.py --smoke
```

The confirmation run executes one seed and ten fresh episodes per S2 condition:

```powershell
python scripts/run_episode.py --confirm --replicates 10
```

Raw traces are local diagnostic artifacts under `results/runs/` and are not
committed without review. API keys, complete sensitive prompts, and unreviewed
raw logs must not be published.

## 9. Acceptance and inconclusive outcomes

### Isolation validity

All of the following must pass:

- S2 session ids differ;
- initial workspace snapshots match;
- DSH commit, config, model/provider/protocol, system prompt, tool schema, and
  task hashes match;
- no resume, fork, skills, MCP, plugin, or filesystem leakage is detected;
- only memory payload hashes differ;
- the memory event proves `R1` was written after S1 and before S2-memory.

### Behavioral signal

For the predeclared primary metric, the confirmation run must observe:

```text
delta first_attempt_compliance >= 0.30
```

and at least one behavior-level signal, such as earlier Decimal use, fewer
initial float implementations, fewer steps to success, or use of R1 before
verifier feedback. This threshold is a Stage 0 demonstration criterion, not a
claim of statistical generalization.

If isolation passes but the signal does not appear, record exactly:

```text
Stage 0 isolation passed, behavioral effect inconclusive
```

Do not change the memory text, task, or metric after inspecting the results.
Only after Stage 0 is isolated and interpretable should the project begin the
plugin track P1 or later E2 work.
